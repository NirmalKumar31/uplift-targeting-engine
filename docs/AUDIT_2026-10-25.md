# Independent audit and Claude follow-up brief

Audited 2026-10-25 against commit `0033e24`, the local warehouse, saved models, and committed dashboard marts. Production source and model artifacts were not changed. This document is the implementation handoff to Claude.

## Verdict

The project has a useful, working core and credible evidence of uplift ranking signal. It is not yet defensible as a rigorously validated profit-optimal deployment. Passing tests does not resolve the inference and policy-validation gaps below. The existing point estimates are real outputs, not invented numbers; their interpretation and uncertainty need correction.

The most important new result: an audit-only, treatment-arm bootstrap of the **existing fixed 41% test policy** gives an approximate 95% interval of **−₽240 to +₽1,253 per 1,000** for its profit advantage over texting everyone. The point advantage is +₽514. This interval includes zero. “About 2×” describes the point estimate; it is not established as a statistically reliable profit improvement. This diagnostic does not validate the different deployed calibrated policy.

## P1 — correct before making strong results or deployment claims

### A1. Outcome-stratified bootstrap removes real sampling uncertainty

**Location:** `src/uplift_engine/evaluation/metrics.py:105`; used by ranking reports and `policy.profit_curve`.

`_stratified_resample` samples separately within treatment × observed outcome cells, fixing all four counts. At 100% depth every bootstrap response-rate difference is consequently identical. In the actual mart, the blanket policy has profit_low = profit_high = 499.861142. A synthetic experiment also reproduces a zero-width ATE interval. Other intervals condition on the observed arm response counts and should not be advertised as ordinary unconditional uncertainty about campaign outcomes. Their distortion is not necessarily identical for every ranking statistic.

**Claude action:** resample customers within treatment arms, keeping `(X, score, outcome)` paired. Keep paired model/policy comparisons on shared draws. Document fixed-model uncertainty separately from training/selection uncertainty. Add coverage simulations across independently generated experiments, including ATE/blanket profit and near-zero effects. Check that the blanket interval has nonzero width in nondegenerate data. Relabel the bootstrap win fraction as a bootstrap fraction, not a posterior probability that one model is better. Recompute all affected marts and copy.

**Additional diagnostic:** 1,000 treatment-arm bootstrap draws, seed 73, saved dev model, unchanged test split and 41% policy: targeted profit CI [396.37, 1656.08], blanket CI [−489.17, 1558.88], paired advantage CI [−239.94, 1252.87], all ₽/1,000. Bootstrap fraction of positive paired advantages: 0.904. These are approximate fixed-model percentile intervals, not a new confirmatory result. Reproduce with `scripts/audit_profit_uncertainty.py`.

### A2. The deployed calibrated decision rule was never evaluated as a complete policy

**Location:** `pipeline.py:220` and `pipeline.py:303`; `models/learners.py:204`.

`evaluate` tests raw-score ranking at dev-chosen depth 41%. `deploy` instead fits an isotonic calibrator on all labeled customers (including the former test set), applies it to scores from a full-data refit, and selects uplift > cost/margin. It then reports sums of these predictions as campaign value. Current policy quantities differ: evaluated depth 41%; full-label OOF profit-maximizing depth 33%; calibrated selected share 155,095/400,162 = 38.76%, before withholding 10%. Refitting after evaluation is reasonable, but it does not establish calibration accuracy or the value of this different policy. OOF-to-refit score transfer is assumed rather than checked. The calibration mart called “test calibration” is an observed ranking-decile chart, not a held-out validation of the deployed calibrated values.

**Claude action:** define the entire learning/calibration/selection procedure before evaluation. Within outer validation folds, fit both learner and calibrator without using the outer fold's labels, then evaluate the exact cost threshold and policy value on the outer fold. Include arm counts, calibration reliability, and paired profit differences against blanket/no-send/response policies. Preserve a separate final untouched evaluation source where available. A new split of the same already-inspected data does not magically recreate an untouched test. Refit for the demonstration afterward; label full-population projections as model-based scenarios.

### A3. “Evaluated once / locked” and lineage claims exceed the evidence

**Location:** README results heading; `docs/methodology.md`; `scripts/build_site.py` generated lede; `pipeline.py:220`.

The original `meta.test_access_log` contains two accesses: 2026-10-24 11:47:10 and 12:08:24 (stored timestamps, not converted local time). The champion changed from an ensemble to S-learner after the leakage correction. Fixing leakage is correct and is disclosed lower in README, but the prominent “evaluated once” wording still misleads. Both entries have `git_sha = unknown`; all current run records also have unknown SHA. The access log only covers one function, results tables are replaced, and the split is regenerated from current data/config rather than checked against a frozen manifest. The log is an audit aid, not an enforced lock.

**Claude action:** describe this as a corrected, reused holdout and give the full evaluation history prominently. Preserve old results. Store dataset digests, feature SQL/version hashes, split ID assignments/hash, config hash, model/calibrator hashes, dirty-worktree status and non-unknown source revision in each run and artifact. Reject mismatched selection artifacts/config/splits. If keeping a “lock,” require an explicit recorded override for repeat evaluation. Do not repeatedly train against these audit findings and keep calling the same test pristine.

### A4. Claimed global future-data guard does not cover purchase inputs

**Location:** `dbt/models/staging/staging.yml`; `stg_transactions.sql`; `feat_product_mix.sql`; `feat_windows.sql`.

`no_future_dates` is attached only to `stg_clients`. Transactions have no cutoff/filter or temporal test; product mix reads raw purchase lines directly. Window counts use `days_ago <= N` without a nonnegative lower bound, so future purchases would enter every recent window. A recent future transaction on one customer could still pass the existing recency range test because `date_diff('day', ...)` can be zero. The supplied purchase snapshot currently has no such rows; this is a guardrail defect, not evidence of remaining purchase-date leakage in today's metrics.

**Claude action:** establish an explicit as-of purchase input with strict timestamp bounds and use it across all feature groups, including product mix. Add negative fixtures containing future timestamps to the actual dbt build. Test null dates and relevant referential integrity. Cite the source of the communication/as-of timing instead of inferring the exact SMS date solely from max purchase date. The competition documentation does support that purchase history precedes communication.

### A5. Serving can authorize sends on unusable records and does not enforce campaign assignment

**Location:** `api.py:90`, `data.py:prepare_features`, `pipeline.py:352`.

`{"clients":[{}]}` returns HTTP 200 with predicted uplift approximately 0.13724 and positive profit/send. Invalid gender, age −999, and string `Infinity` also return 200. Unknown gender silently becomes missing and there is no feature-completeness or domain contract. Missing individual features may be supported deliberately, but all-missing rows should not silently become high-value prospects.

Separately `/score` returns only an economic `send` boolean; it never consults the batch `holdout` action. A caller using it as campaign authorization can defeat the promised control group. The random holdout depends on the position/order and size of the scored population, so adding a customer can change later customers' assignment. This is acceptable for a frozen one-off simulation but not a durable campaign experiment.

**Claude action:** provide a typed feature contract with finite numeric/domain checks and an explicit missing-feature policy; reject unusable rows with 422. Distinguish score/eligibility from authorized campaign action. Use a versioned campaign manifest and stable customer/campaign assignment, and enforce holdout in any send authorization path. Test batch/API prediction parity, holdout preservation, reordered/expanded populations, and absent artifacts. Add readiness that checks model availability; liveness can remain separate.

## P2 — fix before describing the package as complete and portable

### A6. Static HTML uses a different Plotly generation than its JS renderer

**Location:** `scripts/build_site.py`, `docs/index.html` script tag.

The installed Python Plotly is 7.1.0, and committed HTML contains 16 `bdata` fields with `dtype` typed-array payloads. The HTML hard-codes Plotly.js 2.35.2. This is a strong compatibility defect/risk for affected traces; browser reproduction is still required. It is not resolved by successful Streamlit rendering or a static build finishing.

**Claude action:** use Plotly's generated matching JS inclusion (`include_plotlyjs` with a compatible bundled/CDN version), once per page. Add a real browser smoke check asserting each expected trace has nonempty numeric data, including on mobile. Regenerate the site and verify the published version. See the official Plotly migration source below.

### A7. Client search crashes on literal punctuation

**Location:** `dashboard/views/clients.py:18`.

`str.contains` interprets the user input as a regex. Input `[` raises `ArrowInvalid: Invalid regular expression: missing ]: [` and interrupts the page. Confirmed in Streamlit AppTest.

**Claude action:** use literal substring matching (`regex=False`, with an explicit null policy). Add this interaction regression check.

### A8. Age band is factually wrong; demographic anomalies survive cleaning

**Location:** `dbt/models/marts/dim_client.sql` age CASE; `stg_clients.sql`; `feat_demographics.sql`.

Staging keeps ages 14–100. All ages below 25 are labeled `18-24`. There are 4,822 customers aged 14–17 after cleaning, including 1,661 with action `send` and 180 with action `holdout`; the displayed band misstates them as adults. One negative `days_issue_to_redeem` also survives into the feature store. This is a reporting/data-quality finding; it does not establish an unlawful campaign, and no SMS is actually sent by this repo.

**Claude action:** use truthful bands, document age/missing-date handling, and add chronology tests. Add configurable business eligibility rules when turning this historical demo into a campaign. Evaluate subgroup effect/calibration and uncertainty before drawing broad age-based conclusions.

### A9. Surrogate fidelity is evaluated on its own training sample

**Location:** `pipeline.py:426–445`.

The 50k-row surrogate is fitted and evaluated on the same X/target; reported R² 0.98085 is training fit. “98% accuracy” in the supplied brief is also the wrong interpretation of R². The surrogate is unnecessary for exact S-learner uplift explanations: subtract treatment-off contributions from treatment-on contributions where supported; for other learner types a surrogate can remain useful.

**Claude action:** report held-out surrogate R² and error by score decile/segment; distinguish attribution of raw score from attribution of calibrated probability/profit. Keep the useful existing caveat that SHAP explains the model, not causal mechanisms.

### A10. CI bypasses the data transformation path and clean serving setup

**Location:** `.github/workflows/ci.yml`; `tests/conftest.py`; Dockerfile/compose.

Synthetic fixtures precreate final feature tables. End-to-end tests start at `train`, bypassing download, ingest, dbt SQL/tests, mart exports and static generation. CI only parses dbt. `ingest.py` and `cli.py` have 0% coverage. A green CI cannot currently detect A4, A6–A8 or a broken `ute run` orchestration. A fresh clone has no production model/warehouse (both ignored); compose mounts assume those artifacts already exist. There is no `.dockerignore`, so a local Docker build context includes the raw files, warehouse, .venv and other ignored files even though the Dockerfile does not copy them.

**Claude action:** add a small raw-data fixture and run ingest → dbt build → train/evaluate/deploy/explain → marts → API/dashboard/site smoke in CI. Include at least one failure fixture for future data and transaction-field disagreement. Document artifact generation/mount preconditions and test the container startup paths. Add `.dockerignore`. Keep the 32 useful existing tests, but describe their scope accurately.

### A11. Installed-wheel and supported-version contracts are incomplete

**Location:** `config.py:REPO_ROOT`, wheel configuration in `pyproject.toml`.

The wheel packages `src/uplift_engine` only, while runtime config/defaults and CLI dbt assets are resolved via `Path(__file__).parents[2] / configs|dbt`. That works for the editable source checkout, not a normal installation where those repository siblings are absent. Also NumPy >=1.26 is declared while metrics call `np.trapezoid` (introduced in NumPy 2.0). Recent Streamlit APIs in the dashboard should likewise be tested against the advertised minimum rather than assuming 1.38 supports them all.

**Claude action:** either document source-checkout-only execution or package required resources and resolve them with package resource APIs/configurable locations. Test an installed wheel from outside the checkout. Raise minimum versions to tested bounds or provide compatible code; run a supported-version matrix. Lock reproducible CI installs and a tested uv/container toolchain.

### A12. Monitoring and segmentation wording overstates what was measured

**Location:** `monitoring.py`, `dashboard/views/health.py`, `pipeline.py` segment assignment.

SMD <0.1 is a diagnostic for measured covariates, not proof randomization worked or that all causal assumptions hold. Gender is converted to a single ordinal code; a scalar mean can hide category imbalance. Missingness differences are discarded by dropping nulls. PSI compares two portions of the same historical snapshot, so it does not establish temporal stability for new campaigns. Status `fail` is written to a table but does not block deployment. The four customer segments are business heuristics based on CATE/base rate; individual counterfactual response types cannot be observed or identified by these labels. Current calibrated uplift is positive for every customer, so there are no “Do not disturb” customers under the current rule.

**Claude action:** one-hot categorical balance plus missingness checks, state the assumed randomization protocol, label PSI as historical population comparison, and make monitoring status operational if calling it a gate. Clearly label segments as predicted policy groups, not discovered true individual response types.

### A13. Dashboard economics combine different estimands and settings

**Location:** `dashboard/views/simulator.py`, `overview.py`, policy marts and README.

The simulator maximizes the all-label OOF ranking curve over 100 depths and scales it to all clients. The headline campaign value sums calibrated refit predictions and subtracts holdout; the simulator ignores holdout. Its sensitivity table remains precomputed using the original margin even after the margin slider changes. These are different scenarios but appear in one ROI narrative. Choosing the maximum of a noisy curve also creates optimism; pointwise intervals do not cover the uncertainty of the selected optimum. Response and random losses in README are at the champion's 41% depth, not independently optimized baseline policies. A randomly chosen 41% subset is not the expected random policy value.

**Claude action:** label each quantity by population, evaluation source, policy and holdout treatment. Recompute sensitivity from current controls. Include no-send and expected-random baselines; if claiming superiority to an optimized response policy, choose its policy on development data too. Show paired profit differences and economic scenario ranges rather than unstable profit ratios. Call modeled extra conversions “additional buyers” unless the outcome actually counts purchases. Constant basket × gross margin is a documented assumed utility, not observed incremental profit or causal basket revenue.

## Lower-priority implementation issues

- `models.tuning.enabled` and `n_trials` are accepted but unused; don't advertise operational tuning. `reference_date` lives in dbt, outside the stated single-source YAML config.
- Validate positive configured margin, nonempty/valid model candidate sets and ensemble size. Unequal treatment assignment needs a corrected/weighted class-transformation learner or an explicit 50/50 precondition; the current near-50/50 dataset makes this approximation small.
- `load_raw` records the configured expected hash, without independently validating the file there. The CLI does validate immediately before loading, but direct calls do not establish verified lineage. Verify actual input hashes at the loading boundary.
- Artifact/table writes are not one atomic versioned release. A failed rerun can leave models, marts and scores from different generations; cached API bundles do not reload automatically. Record a release ID and document/restrict activation.
- Dashboard cache keys omit parquet modification/version information. Refreshes can serve stale marts after a rebuild until the cache is cleared. Use a release ID or file fingerprint.
- Add metric validation for empty arrays, nonbinary treatment/outcome, nonfinite scores, invalid depths and degenerate perfect-Qini denominators. Existing 100% metric line coverage does not test these contracts.
- The “2.1× prior project” comparison already discloses different splits. Retain that qualification and avoid interpreting it as a controlled improvement attributable to features alone.
- Keep dataset provenance/usage terms separate from the MIT code license and document redistribution of granular public-data marts. No legal conclusion was attempted in this audit.

## Claude's recommended work order and acceptance criteria

1. Correct the README/site/methodology claims immediately: reused test, approximate point estimates, unvalidated deployed calibration and profit uncertainty. Preserve historical outputs.
2. Fix A1 and build a complete nested/outer-fold policy assessment for A2; publish paired policy differences. Do not search for a favorable test result.
3. Implement as-of inputs, raw fixture dbt integration, durable provenance and artifact consistency (A3/A4/A10).
4. Fix unusable API inputs and enforce campaign assignment where sends are authorized (A5).
5. Repair static renderer, literal search, truthful bands, held-out fidelity and ROI consistency (A6–A9/A13).
6. Test clean checkout, installed wheel and containers; document supported execution modes (A10/A11).
7. Return a finding-by-finding disposition with changed files, regression evidence, new metrics/intervals and remaining limitations. Keep exploratory estimates separate from confirmatory evaluation.

No new predictive model family is needed to address these findings. Better validation and consistent decision semantics matter more than adding features or increasing the reported Qini.
